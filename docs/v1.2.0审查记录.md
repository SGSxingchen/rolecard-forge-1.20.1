# v1.2.0 世界任务/副本公告审查记录

> 审查基线：`main` 的 `2a84b54`（v1.1.2）。本记录仅描述落地方案；未运行 Gradle、Java、Forge 或 Minecraft。本机只允许静态审查，动态构建与运行验证必须放在 GitHub Hosted Runner。

## 1. 已确认的产品与兼容边界

- 世界任务是**服务器当前全局公告**，独立于每位玩家的 `CharacterCard`、审核状态和 Capability；不更改角色卡数据版本 2，也不移动既有 NBT 键。
- 本期只保存、展示、编辑、同步公告。不得加入任务判定、自动进度检测、任务世界协调、周目切换、传送、奖励、道具继承、数据库或 HTTP。
- 管理员自由填写的文本原样展示；只有进入服务端、SavedData 与网络前的边界校验会拒绝控制字符、格式字符、非法 Unicode、超长字符或超长 UTF-8 数据。
- 已确认用户保护项：`docs/发布v1.1.0核验记录.md` 目前为未跟踪文件。整个开发、暂存、提交、清理和发布流程均不得读写以外的变更，尤其不得删除、修改、暂存或提交它。

## 3. 推荐的数据、存档和服务边界

建议采用 `MissionBoardSnapshot`（不可变 DTO）与 `MissionObjective` DTO，配套单独 codec/NBT 转换。字段至少为：

```text
dtoVersion、published、title、summary、objectives[{text, completed}]、rules、notes、
instanceName、instanceCode、difficulty、playerCountText、timeLimitText、status、
revision、updatedAt、editorSummary
```

建议约束（可集中在 DTO/codec 常量中，网络、命令、UI 保存与 NBT 加载共用）：

- `title`、`instanceName`、`instanceCode`、`difficulty`、`playerCountText`、`timeLimitText`、`editorSummary` 采用短文本上限；`summary`、`rules`、`notes` 采用多行上限；每项同时限制字符数和 UTF-8 字节数。
- `objectives` 使用有序 `List`，应限制总数（例如 16）与每项长度；`rules` 可选有序列表（例如 12）或一个受限多行文本。所有 NBT 读取必须检查 tag 类型、截断/丢弃超限条目、缺键安全默认。
- `status` 建议独立枚举：`DRAFT`（未开放）、`ACTIVE`（进行中）、`COMPLETED`（已完成）、`CLOSED`（已关闭）；未知值回退 `DRAFT`。DTO 版本未知或 NBT 非法时回退空公告，绝不读取为未验证文本。
- SavedData 保存 `published` 与快照；`clear` 生成 revision 更高的未发布快照并 `setDirty()`。重复内容保存不增加 revision、不广播；有效替换才递增 revision（`Long.MAX_VALUE` 时安全回绕至正值），并记录服务端时间和管理员摘要。
- `MissionBoardService` 仅在服务器线程使用，建议公开 `getSnapshot(server)`、`replace(server, actor, expectedRevision, incoming)`、`update(server, actor, mutator)`、`clear(...)`、`sync(player)`、`syncAll(server, notify)`。外部系统只能提交经过同一 codec/校验的 DTO，不能直接操作 SavedData 或静态 Map。

这样世界备份会自然包含 `Overworld/data` 的公告，管理员离线不会影响数据；未来数据库、远端验证或任务模组可在服务器线程调用 Service，再由本服务保存、增 revision 和广播。

## 4. 网络与权限建议

`RoleCardNetwork` 目前协议为 `"3"`，已注册的 discriminator 为 0–8。为满足“不破坏旧包语义”，应保持其顺序不动，追加任务包，例如：

| 方向 | 建议包 | 责任 |
| --- | --- | --- |
| S2C | `MissionBoardSyncPacket` | 仅携带受限、codec 后的权威快照；客户端仅当 `incoming.revision >= cached.revision` 时替换，旧 revision 丢弃。 |
| S2C | `OpenAdminMissionPacket` | `/rolecard mission edit` 成功时打开管理员面板，并带当前快照。 |
| C2S | `SaveMissionBoardPacket` | 管理员提交“基础字段/目标/规则/状态”的编辑意图和 base revision；服务端以 `context.getSender()`、权限 2、revision、codec 校验为准。 |

若用 `ClientFeedbackPacket` 复用反馈，需让客户端在 `AdminMissionScreen` 时也显示反馈；也可追加任务专用反馈包。无论哪种方式，普通客户端不应拥有改写 snapshot 的 C2S 包。登录、换维度、配置重载须发送 S2C 权威快照；替换成功后向所有在线玩家发送快照。通知只在**有效发布且内容/revision 改变**时发送一次，使用可点击文本打开任务页；新玩家登录仅同步，不强制弹窗。

## 5. UI 最小落地

- 玩家 `RoleCardScreen` 把三个页签扩为“身份 / 生平 / 六维 / 世界任务”。任务页始终只读；顶部使用状态中文徽章、修订号/更新时间，副本信息用紧凑信息格，主体为可滚动的简介、序号目标、规则和备注。完成目标降弱但仍可读。
- 没有 `published` 任务时不绘制空的大内容卡，只显示居中的空态：**“当前没有已发布的世界任务”**及简短说明。
- 仅权限 2 的玩家在任务页/底栏获得“任务管理”入口；是否显示可由服务器下发的 `canManage` 或仅由服务端 `OpenAdminMissionPacket` 的命令入口决定。为防客户端伪造，显示逻辑不构成授权，保存包必须再验权限。
- 新增 `AdminMissionScreen`，复用 `ArchiveLayout`/`ArchiveUi`/`ArchiveEditBox`/`MultiLineBiographyBox`，用分页或内容滚动满足 320×240：基础/内容（简介、规则、备注）/目标与状态。应显示字数、可增删目标、反馈；发布按钮提交快照而不是客户端直接广播。
- `ArchiveLayout.Frame.tab(int)` 目前硬编码三页。应改为 `tab(index, count)` 或新增任务页专用 tab 布局，随后同步修改 `UiLayoutAssertions` 和 smoke 的页数断言；不要靠缩小固定三页按钮硬挤第四页。

## 6. 命令树建议

```text
/rolecard mission view
/rolecard mission edit
/rolecard mission clear
/rolecard mission status <draft|active|completed|closed>
/rolecard mission title <文本...>
/rolecard mission summary <文本...>
/rolecard mission instance <名称...>
/rolecard mission objective add <文本...>
/rolecard mission objective set <序号> <完成true|false> [文本...]
/rolecard mission objective remove <序号>
```

实现上将 `view` 放在无 `requires` 的节点；`edit` 需在线的权限 2 管理员（控制台返回明确失败），其他写操作的节点统一 `.requires(s -> s.hasPermission(2))`。状态和目标索引应提供 Brigadier 建议补全并给出 1 基序号的错误反馈。命令改动也必须经 `MissionBoardService`，以获得一致的校验、修订、持久化、同步和去重通知。

现有 CI 路径为 `.github/workflows/ci.yml`：`quality-gates → build → {dedicated-server, client-smoke} → regression-report`；真实运行均在 Hosted Runner。建议新增 `scripts/ci/rolecard_v120_mission.py` 并从 `quality-gates` 调用，至少覆盖：

2. revision 冲突、重复相同内容保存幂等且不重复广播；
3. 普通玩家写命令/C2S 编辑/状态变更被拒绝；
4. 登录、换维度、管理员发布广播的事件与 Service 入口；
5. 新任务网络注册的唯一 discriminator、显式 `PLAY_TO_CLIENT`/`PLAY_TO_SERVER`、C2S `getSender()`、长度限制；
6. 320×240、427×240、854×480、1920×1080 下四个玩家页签和管理员任务页的安全区、不重叠、最小点击面积；
7. `ClientSmokeProbe` 初始化玩家任务页、管理员任务页、逐页切换与稳定 tick。

同时需扩展 `quality_gates.py` 的预期网络包集合和 CI-only 探针文本契约，更新 `regression_report.py` 的覆盖矩阵。专服 smoke 现有 `help rolecard` 能验证根命令注册；可将检查增强为 `help rolecard mission`，但它不能代替有玩家的权限/广播会话验证。

## 8. 版本、提交与正式发布流程

- 版本唯一来源是 `gradle.properties` 的 `mod_version=1.1.2`；将其改为 `1.2.0` 后，`processResources` 自动展开 `mods.toml`，`build.gradle` 的 Jar 版本也随之更新。
- 现有 `package_release.py` 只校验 Jar 的 `modId`，未明确断言压缩包中 `mods.toml` 的 `version`。本期应补足 `modId=rolecard` 与 `version=1.2.0` 的 Jar 内校验，发布前仍额外执行 ZIP 完整性与 SHA-256 复核。
- 工作流只读 `contents` 且明确“不发布 Release”。因此发布必须在全绿后由具备仓库写权限的 GitHub CLI/API 操作：定位本提交的 run，确认五个必需 job 都 `success`，从**该 run**下载 `rolecard-release-jar` 与 `rolecard-sha256`，只接受唯一 `rolecard-1.2.0.jar`，必要时重命名为 `rolecard-forge-1.20.1-1.2.0.jar`，校验 ZIP、`META-INF/mods.toml`、大小和 SHA-256。
- 之后创建 annotated tag `v1.2.0` 指向全绿提交并推送 tag；以该 tag 建立非 draft、非 prerelease 的 Release，上传正式 Jar 与同名 `.sha256`。不得使用工作区旧 Jar、CI 探针 Jar，且不得覆盖任何旧 Release。若 GitHub 权限、Actions 或 Release 上传失败，应明确报告为阻塞原因。

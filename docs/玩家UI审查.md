# 玩家角色卡 UI 审查（v1.1.0 现状）

> 审查范围：`RoleCardScreen`、`MultiLineBiographyBox`、玩家端同步入口及其服务端交互边界。本文是 UI 重构前的事实记录与最小改造建议；不改变角色卡数据、审核状态机或既有 C2S 包语义。

## 1. 当前实现与问题定位

### 1.1 画面骨架

玩家界面唯一的 Screen 是 `com.rolecard.client.RoleCardScreen`。它以一个**固定 238 px 高**的面板承载全部页面：

```text
top +  0..28   标题条（标题居中；状态、剩余点数、版本同一基线）
top + 30..48   三个原版 Button 页签
top + 42/43    页面说明文字（与页签实际重叠）
top + 48..178  身份输入 / 生平输入 / 六维六行
top + 184      锁定或退回提示
top + 208..228 关闭、保存草稿、提交角色卡
top + 238       面板结束
```

布局由 `left/top/cardWidth` 及大量 `top + 常量` 直接散落在 `init`、`render`、`renderStats` 和 `mouseClicked` 中；没有可测试的布局模型，也没有安全边距、内容区或底栏区的独立矩形。

### 1.2 可复现的真实叠层/越界

| 情形 | 现有计算 | 结果 |
| --- | --- | --- |
| 所有分辨率 | 页签为 `top+30..48`，身份标题和六维说明在 `top+43`，生平说明在 `top+42` | 文本落在页签高度内；`super.render` 最后绘制 Button，会把说明压在下面，正是截图中的页签遮挡。 |
| 320×240 | `top=max(4,(240-238)/2)=4`，面板到 `y=242` | 面板本身越过屏幕下沿 2 px；没有给其他 HUD、GUI 缩放或提示留安全区。 |
| 320×240 与 427×240 | 固定高度仍为 238，底栏到 `top+228`，底部只余约 8 px（320×240 时甚至面板越界） | 关闭/保存/提交贴近边缘，悬浮提示没有安全位置。 |
| 六维页 | 第六行 `top+176..195`；退回/锁定提示从 `top+184` 开始 | 最后一项六维与退回原因/锁定说明重叠。 |
| 所有页面 | 反馈文字 `top+214` 正落在按钮 `top+208..228` 内，且 Button 后绘制 | 网络发送反馈会被底栏遮盖，不能作为可靠状态反馈。 |
| 中等及宽屏 | 面板最大宽度仅 430 px；六维数值固定靠右，减/加仍位于最右 64 px | 大量无意义横向空白，名称→数值→操作的阅读动线被切断。 |

### 1.3 控件与可用性缺口

- 页签、底栏直接使用未换肤的原版 `Button`，而背景、行背景是蓝黑自绘矩形，视觉语言割裂；三枚底部按钮宽度为 48、78、80 px，主次关系和间距不统一。
- 六维的 `+/-` 不是 Widget，而是在 `mouseClicked` 内按坐标命中。它们没有 Tab 焦点、旁白、原生按压/禁用态，也只有 16×15 px 命中区，小于要求的 20×20 px。
- 身份输入框使用原版 `EditBox`，但没有可见标签-输入的栅格、必填/格式错误的字段级提示、焦点统一描边或剩余字数。`年龄` 只在点击保存后才因 `Integer.parseInt` 失败给出笼统文本。
- `showPage` 只设置 `visible`，未按审核状态设置输入框或操作按钮的 `active`/只读外观。`APPROVED` 与默认 `PENDING` 时，输入框、保存、提交仍像可操作控件；只有加点点击会先以 `editable()` 拦截。服务端仍会拒绝，因此这是**视觉与交互状态不一致**。
- 客户端 `CharacterCard.canPlayerEdit()` 固定把 `REJECTED` 视作可编辑，未反映服务端 `workflow.allowRejectedEdits` 或 `allowDraftEditsWhilePending` 配置。UI 只能作保守展示，权威判断仍应留在服务端；不要为了 UI 把配置或状态机复制进客户端。
- `feedback` 是永久字符串、没有成功/警告/错误类型和超时，也无法从现有 `CardSyncPacket` 区分“成功同步”与“revision 冲突/服务端拒绝”。目前服务端错误主要以聊天 `sendSystemMessage` 告知。
- `effectText` 只在鼠标位于两个小按钮时显示 tooltip，无法满足“整项可悬停”。tooltip 不受安全区策略约束。

### 1.4 生平多行控件的实际风险

`MultiLineBiographyBox` 虽继承 `EditBox`，却完全覆盖 `renderWidget`：只手工绘制换行后的文本和一条 1 px 顶边。

1. 没有绘制插入光标、选择高亮、水平/垂直裁剪区、完整四边焦点框或滚动条；输入时光标不可见，文本可能视觉上越出预期区域。
2. `firstLine` 仅在滚轮时变化，光标移动或追加内容时不会自动滚到可见范围；“可编辑”的底层行为与“自绘多行显示”没有统一布局。
3. 自绘文字没有 `PoseStack` 裁剪，长行、换行边界、选择和提示都无法获得真正的内容视口保证。
4. 空内容提示条件依赖 `Font.split` 返回空列表，而不是直接判断输入值；提示逻辑不够明确。
5. 该控件同样没有审核锁定阅读态；隐藏时仍保留实例，但不应作为可编辑外观复用。

## 2. 与 UI 重构相关的文件清单

| 文件 | 作用 | 重构注意事项 |
| --- | --- | --- |
| `src/main/java/com/rolecard/client/RoleCardScreen.java` | 玩家三页 Screen、保存/提交/六维意图包 | 主要替换对象；保留 `SaveDraftPacket`、`SubmitCardPacket`、`AdjustPointsPacket` 的调用和 revision 读取。 |
| `src/main/java/com/rolecard/client/MultiLineBiographyBox.java` | 当前伪多行编辑框 | 应改为统一样式的可裁剪多行编辑/只读阅读视图；不得继续用无光标的 `EditBox` 皮肤冒充完整编辑器。 |
| `src/main/java/com/rolecard/client/ClientCardCache.java` | S2C 卡片快照缓存 | 可作为“revision 更新后清空本地拟加点、刷新反馈”的唯一输入；无需改变 DTO。 |
| `src/main/java/com/rolecard/client/RoleCardClient.java` | I 键打开玩家 Screen | 不需要改业务逻辑；可作为客户端探针打开 Screen 的入口参考。 |
| `src/main/java/com/rolecard/data/CharacterCard.java` | 文本上限、状态与本地便捷判断 | 状态/数据语义不改；UI 不应以 `canPlayerEdit()` 取代服务器配置校验。 |
| `src/main/java/com/rolecard/network/{SaveDraftPacket,SubmitCardPacket,AdjustPointsPacket}.java` | 既有玩家请求 | 不修改网络协议；若要面板内精确失败反馈，需另行最小化增加**可选 S2C UI 反馈 DTO**，并保留聊天兜底。 |
| `src/main/java/com/rolecard/service/RoleCardService.java` | 权威 revision、状态和同步 | 维持为唯一判定方；UI 仅据同步快照更新，不复制业务规则。 |

## 3. 最小重构方案（供统一设计稿合并）

### 3.1 玩家线框

```text
屏幕安全边距（至少 8 px，受 HUD 留白约束）
┌────────────── 居中档案册主面板（最大宽度；小屏缩放内容区） ──────────────┐
│ 角色档案                                  [草稿/待审核/已批准/已退回] [修订 #] │
│ ┌──────── 身份 ────────┬──────── 生平 ────────┬──────── 六维 ────────┐ │
│ └──────────────────────┴──────────────────────┴──────────────────────┘ │
│ ┌──────────────────────── 当前页面内容面板（固定内边距） ──────────────┐ │
│ │ 身份：名称整行；年龄 | 性别；字段说明/错误或锁定阅读值               │ │
│ │ 生平：标题 + 字数；带四边框、内边距、裁剪和滚动条的编辑/阅读区       │ │
│ │ 六维：页首 [剩余 N 点]；宽屏两列属性卡，小屏单列；整卡 tooltip        │ │
│ └─────────────────────────────────────────────────────────────────────┘ │
│ [面板内反馈：成功 / 警告 / 错误]                         关闭  保存草稿  提交 │
└─────────────────────────────────────────────────────────────────────────┘
```

建议所有纵向位置由 `ScreenLayout` 输出的 `Rect` 取得：`safeBounds`、`header`、`tabs`、`content`、`feedback`、`footer`，页面内容再从 `content.inset(8)` 派生。页签与内容区间必须保留至少一个基础间距，底栏从独立 `footer` 取位，不能由内容最后一行倒推。

### 3.2 保留行为、替换呈现

- 新建客户端纯 UI 层（例如 `RoleCardUiTheme`、`RoleCardLayout`、`RoleCardButton`），集中 token：底色、表面色、主/次描边、标题/正文/弱文字、强调、成功、警告、错误、基础间距 `8`、控件高 `20/22`、切角尺寸。
- 自定义小型 `AbstractButton` 子类只替换 `renderWidget`，保留原生焦点链、Tab 导航、旁白消息和点击行为。页签、关闭、保存、提交、六维步进器都使用同一套皮肤和状态色；六维按钮最小 20×20。
- 以统一 `editable` 展示策略把所有字段、保存、提交、步进器同步设为 active/只读；锁定时换成阅读文本或禁用外观，并给出原因 tooltip。服务端仍是最终裁判。
- 六维不要再依赖 `mouseClicked` 手算命中。每一项应有名称、当前/草案值、短收益摘要、紧凑 `− 数值 +`，属性卡整体可悬停展示完整 Attribute 映射。宽度允许时两列，窄屏单列；仅内容确实超过视口时才裁剪/滚动。
- 生平编辑区应拥有明确 viewport：填充、四边描边、内边距、滚动位置、滚动条及字数；阅读锁定态使用同一内容区的换行文本而非灰掉的输入框。
- 面板反馈需有类型和消退时间。现有同步只能可靠表示“服务器数据已刷新”；若必须区分 revision、权限、校验失败，需要一个很小的 S2C 结果码适配，不能假称仅靠现有 C2S 包已能判断成功。

## 4. 布局与自动验证建议

将 `RoleCardLayout.compute(width, height, page, statCount)` 做成无 Minecraft 依赖的纯函数，返回不可变 `Rect` 集合与列数。自动测试至少覆盖 320×240、427×240、854×480、1920×1080，并断言：

1. 主面板、页签、内容、反馈、底栏均在安全区；
2. 页签不与内容说明相交，内容不与底栏/反馈相交；
3. 每个可点击 Rect 非空，步进器宽高均不少于 20 px；
4. 六维两列仅在列宽满足摘要与步进器时启用，否则回退单列；
5. 玩家各页与管理员 Screen 的根布局均可初始化，切页后 Widget 边界仍在安全区。

测试只证明几何和生命周期，不应宣称已自动验证“像素美观”。CI 客户端探针目前只确认 TitleScreen 稳定，尚未打开 `RoleCardScreen`，需要后续在可控测试快照下补入打开、切页与稳定 tick 探针。

## 5. 实施风险与边界

- **最大风险是小屏高度而不是颜色**：当前 238 px 固定高度已在 240 px 高度失败；不能靠压缩字体修补，必须让布局有小屏单列、必要时内容滚动和独立底栏。
- **不要把服务端配置镜像为客户端权威逻辑**：客户端可做保守禁用和说明，真正编辑资格、revision、点数始终由 `RoleCardService` 决定。
- **不要把“已发送”当“已保存”**：现有包只有请求和随后的全量同步/聊天错误，若不增加反馈 DTO，就只能显示“正在请求/已收到刷新”，不能精确显示保存成功或失败原因。
- **管理员界面也使用相同的固定 238 px 与灰按钮模式**（`AdminRoleCardScreen`），必须和玩家布局系统一起迁移；但其字段、审批操作及目标 DTO 不应被玩家重构改动。

# 未来远端同步与联网验证设计（仅设计，不含网络实现）

## 稳定数据边界

- 稳定玩家标识只使用 Minecraft UUID；游戏名与角色名称均为可变展示字段。
- v1.1.0 的服务器 NBT 数据版本为 `2`，包含身份、`biography`、六维、`availablePoints`、审核状态、退回原因和 `revision`。NBT 版本与远端 DTO 版本独立演进。
- 建议远端交换使用不可变 DTO，例如：

```text
CardDto {
  schemaVersion,
  playerUuid,
  originalPlayerName,       // 仅作展示/审计快照，非身份键
  identity { roleName, age, gender },
  biography,
  stats { bulk, strength, coordination, reflex, spirit, luck },
  availablePoints,
  status,                  // DRAFT / PENDING / APPROVED / REJECTED
  rejectionReason,
  revision,
  submittedAt,
  updatedAt
}
```

- 不把客户端草案、按钮状态、屏幕滚动位置、管理员权限或 AttributeModifier 直接放进远端 DTO；它们不是可跨服务器信任的业务事实。
- 生产逻辑未来可在 Capability 外增加薄的 `CardService` 门面：读取、校验、状态迁移和写入仍在服务器主线程；导入导出只处理不可变 DTO。当前不引入空接口、数据库客户端或 HTTP 依赖。

## 状态、版本与幂等

- 每次卡片有效变更递增 `revision`。远端写入、后台审核或重新投递需携带 `playerUuid + revision` 幂等键，绝不采用“最后到达者覆盖”。
- 状态迁移必须由服务端验证。远端不能把 `PENDING` 或 `APPROVED` 静默降级为可编辑草稿；退回/解锁也必须留下操作来源、时间和可选原因。
- 待审核索引按玩家 UUID 去重。重复的同 revision 投递只确认已处理；更高 revision 更新同一条记录；更低 revision 拒绝并返回当前版本。
- 导入 v1 DTO 时，缺少的生平、点数、状态、原因和修订号使用与本地 v1 NBT 迁移一致的安全默认值；不得清空原有身份或六维。

## 异步与一致性

- 主线程只提交 DTO 快照到异步队列；异步线程绝不直接访问玩家实体、Capability 或世界对象。
- 重试使用指数退避、最大次数和可观测失败队列。成功回执必须回到主线程，并再次检查 `playerUuid + revision` 是否仍是当前版本。
- 冲突默认“本服务器权威”：远端版本落后时拒绝或仅确认；远端版本领先时进入人工审计或明确的管理员导入动作。禁止静默合并六维、点数和审核状态。
- 点数增减必须以服务器审计事件或受控余额变更表示，不能接受客户端/远端传来的“我已消费总数”作为事实；导入会重新校验六维范围与余额不为负。

## 隐私与联网验证

- 只传输完成业务所需的 UUID、版本、身份、生平、六维、审核状态和时间。年龄、性别、生平可能属于个人化资料；接入前应向服主和玩家明确告知用途、保留期限、导出和删除策略。
- 请求必须带时间戳、随机数、服务端标识与服务端密钥签名；验证端校验签名、重放窗口、版本兼容性与权限。密钥只存服务端安全配置，绝不下发客户端或写进日志。
- 外部审核系统只能提出建议或返回签名结果；Minecraft 服务端仍是最终状态机与属性应用权威。验证失败只影响远端同步状态，不能让客户端绕过本地审核、点数或 revision 校验。

## 后续联网验证入口

未来接入点为 `CardService` 的导入/导出任务、审核事件和登录后同步钩子。开始实现前应单独确定：远端是否保存全文生平、审核原因的可见范围、冲突人工处理界面、离线档案查看能力与数据删除流程；这些均不属于 v1.1.0。

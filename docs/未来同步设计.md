# 未来远端同步与联网验证设计（仅设计，不含网络实现）

## 稳定数据边界

- 稳定玩家标识只使用 Minecraft UUID；游戏名与角色名称均为可变展示字段。
- 交换 DTO 使用版本号，例如 `CardDto{schemaVersion, playerUuid, identity, stats, revision, updatedAt}`。服务端 NBT 的版本与远端 DTO 版本独立演进。
- 生产逻辑未来应在 Capability 外增加薄的 `CardService` 门面：读取/验证/更新仍在服务器主线程，导入导出通过 DTO 进行。当前不引入该接口、数据库客户端或 HTTP 依赖，避免空抽象。

## 异步与一致性

- 主线程只提交不可变 DTO 到异步队列，异步线程绝不直接访问玩家实体、Capability 或世界对象。
- 每次写入携带 `playerUuid + revision` 幂等键；重试应采用指数退避、上限和可观测失败队列。
- 冲突默认“本服务器权威”：远端版本落后则覆盖；远端版本领先则进入人工审计或按显式导入操作覆盖，不能静默混合六维。
- 成功回执回到主线程后只更新同步状态，不直接覆盖本地角色数据，除非执行受控导入。

## 隐私与联网验证

- 只传输完成业务所需的 UUID、版本、身份与六维；年龄、性别等个人化字段需取得服主与玩家的明确告知/同意，并提供导出/删除策略。
- 请求必须带时间戳、随机数、服务端密钥签名；验证端校验签名、重放窗口、服务端标识和版本兼容性。密钥仅存服务端安全配置，绝不下发客户端或写进日志。
- 未来验证系统的接入点是 `CardService` 的导入/导出任务和登录后同步钩子；验证失败只影响远端状态，不能让客户端绕过本地服务端权威校验。

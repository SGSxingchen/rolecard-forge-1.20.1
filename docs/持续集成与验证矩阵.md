# 持续集成与验证矩阵

> **执行边界**：本项目的真实 Gradle、Forge、Minecraft 客户端和专用服务器验证只允许在 GitHub Actions 的 GitHub Hosted Runner 中运行。本地只允许 Git、文本、YAML、Python 静态检查及 GitHub CLI 查询；`build/` 中的历史文件不是 CI 结果，不能作为发布或通过依据。

## 触发与总览

工作流文件为 [`.github/workflows/ci.yml`](../.github/workflows/ci.yml)。它会在推送到默认分支、拉取请求，以及手动触发时运行。所有下列 Job 都是必需项；末尾的 `regression-report` 会核对它们是否都成功，任一 Job 失败、被跳过或缺失都会使总结果失败。

| Job | 运行环境 | 目的 |
| --- | --- | --- |
| `quality-gates` | Hosted Runner（只做静态检查） | 阻止资源、元数据、网络注册和依赖完整性问题进入构建。 |
| `build` | Hosted Runner / Java 17 | 运行 `clean build`，筛出唯一可发布 Jar 并校验内容与校验和。 |
| `dedicated-server` | Hosted Runner / Java 17 | 安装固定的 Forge 1.20.1 专用服务器，加载本次 Jar 后作真实启动与基础命令验证。 |
| `client-smoke` | Hosted Runner / Java 17 / Xvfb + Mesa | 启动真实 Forge 客户端，确认完成初始化并稳定到可识别的主菜单成功标志后正常退出。 |
| `regression-report` | Hosted Runner | 汇总必需 Job、日志与本文件定义的覆盖矩阵。 |

工作流不使用 `continue-on-error` 伪造成功。Forge 安装器和关键下载固定 Minecraft `1.20.1`、Forge `47.4.10`；下载失败仅允许有限重试一次，关键文件会做存在性和 SHA-256 校验。

## 静态质量门禁

`quality-gates` 针对本模组而非通用业务样例进行检查：

- `assets/rolecard` 等资源路径为小写，JSON、TOML 和 `pack.mcmeta` 可解析；
- `mods.toml`、`gradle.properties` 与源码中的 modid、版本、Minecraft/Forge 版本保持一致；
- 资源引用可定位，语言资源与命名空间不漂移；
- `common` 侧不得直接引用 `net.minecraft.client` 或本模组 `client` 类，避免专服类加载失败；
- 网络包的收发方向明确、注册编号不重复；客户端意图包由服务端以实际发送者为准处理；
- Gradle Wrapper、校验配置和 Forge 安装/下载关键文件完整，固定版本与哈希未被意外改动。

静态门禁只能尽早发现结构问题，不能代替真实 Forge 启动、联机和界面验证。

## 构建产物与可追溯性

`build` 使用 Java 17 执行 `./gradlew clean build --no-daemon`，从构建输出中只选择一个可发布模组 Jar。`*-sources.jar`、`*-javadoc.jar`、`*-dev.jar`、`*-plain.jar` 和测试探针均不得作为发布产物。工作流会打开 Jar，断言其中含 `META-INF/mods.toml` 且 `modId="rolecard"`，并上传：

- `rolecard-release-jar`：唯一可发布 Jar；
- `build-logs`：Gradle 构建日志；
- `rolecard-sha256`：发布 Jar 的 SHA-256 清单；
- `dedicated-server-logs`、`client-smoke-logs`：对应真实启动日志（即使 Job 失败也应保留）。

下载发布 Jar 后，应先用 SHA-256 清单核对完整性，再放入 Forge 1.20.1 / 47.4.10 的 `mods` 目录。CI 不会创建 GitHub Release。

## 真实运行验证

### 专用服务器（必需）

专服 Job 将本次 `rolecard-release-jar` 放入新安装的 Forge 专服 `mods` 目录，写入 EULA 后启动。它必须等待 Forge 的完成启动标志（例如 `Done`），确认 `rolecard` 加载，执行基础命令和 `save-all flush`，再以正常命令停止。日志同时必须不存在 FATAL、`NoClassDefFoundError`、客户端类泄漏、Mixin apply error、crash-report 等严重故障。

该 Job 的自动化功能断言至少包括：模组可由专服加载、`/rolecard` 命令已注册且可调用。若工作流提供只存在于 CI 工作目录的临时探针，它绝不打进 `rolecard-release-jar`。

### 单客户端冒烟（必需）

客户端 Job 在 Xvfb 与 Mesa 软件渲染环境下运行本次构建 Jar。通过标准输出/日志中的可识别初始化或主菜单成功标志确认稳定启动，再正常退出；同时检查 crash-report 和严重错误。该 Job 证明客户端初始化路径可用，**不**等同于已经完成多人显示或 UI 交互验收。

## 覆盖矩阵

下表是工作流配置的覆盖判定口径，`regression-report` 应在每次运行中生成并随工件保存。表内状态描述的是门禁能够提供的验证能力，**不表示任何提交已经实际通过**。状态含义：**完整自动覆盖**表示 CI 有可靠断言；**部分覆盖**表示仅检查到部分前提；**未覆盖**表示本轮没有自动断言；**人工待测**表示必须由人工在真实联机环境完成。不得把“构建成功”误记为功能通过。

| 验证目标 | 当前 CI 判定 | 证据/边界 |
| --- | --- | --- |
| Java 17 clean/build、发布 Jar 元数据与 SHA-256 | 完整自动覆盖 | `build` 的 Gradle、Jar 内容和清单断言。 |
| 资源格式、mod 元数据、公共侧客户端引用、网络注册规则 | 完整自动覆盖（静态） | `quality-gates`；仍不替代运行时加载。 |
| 专服加载 `rolecard`、命令注册和基础调用 | 完整自动覆盖 | `dedicated-server` 启动日志与控制台命令。 |
| Forge 客户端初始化并到达可识别主菜单成功标志 | 完整自动覆盖 | `client-smoke` 的 Xvfb/Mesa 真实启动日志。 |
| Capability 默认值、NBT 往返与损坏/缺键 NBT 容错 | 部分覆盖 | 仅在 CI 临时探针或可靠 GameTest 实际启用时可升级为完整覆盖；否则保留人工验证。 |
| 六维 AttributeModifier 重复应用不累积 | 部分覆盖 | 静态 UUID/先删后加规则可检查；需要运行期探针或 GameTest 才能完整证明。 |
| 管理员权限拒绝 | 部分覆盖 | 专服可验证命令存在；权限等级 0 的拒绝需要可控玩家会话/探针才是完整覆盖。 |
| 网络方向、恶意越权包拒绝 | 部分覆盖 | 静态方向和服务端 sender 规则可检查；恶意包运行期注入需要专门探针。 |
| 死亡 clone、退出重连、跨维度同步 | 未覆盖 | 需要可靠的生命周期测试会话；不可由单次启动冒充通过。 |
| 两客户端三种名称显示（聊天、头顶、Tab）与一致性 | 人工待测 | 需两名真实客户端和与整合包冲突模组组合测试。 |
| UI 编辑、不同分辨率布局 | 人工待测 | 单客户端冒烟不操作 GUI。 |
| 装备/药水/其他属性模组叠加 | 人工待测 | 需目标整合包实测。 |

### 本轮未纳入必需 Job 的后续矩阵

双客户端联机及完整生命周期恢复会显著增加 Hosted Runner 的图形、账户/离线会话与时序不确定性。本轮不把不可靠脚本伪装成强制绿灯；后续如需纳入，应建立独立、可重复的矩阵：

1. 本地临时或 CI 专用测试模组创建两个受控测试会话，不修改发布 Jar；
2. 覆盖权限 0/2、伪造客户端包、死亡 clone、重连、主世界/下界/末地换维；
3. 用服务器日志、持久化 NBT 与客户端收到的同步包三种证据交叉断言；
4. 两客户端依次检查聊天、头顶、Tab 的 `VANILLA`、`ROLE`、`HIDDEN` 三模式；
5. 仅当在 Hosted Runner 连续稳定后，才将其提升为必需 Job；否则继续保持人工待测并记录失败日志。

## 故障诊断

1. 在 Actions 页面打开失败 Job，先下载同名日志工件；不要用本地历史 `build/` 推断结果。
2. `quality-gates` 失败时，按报错修正路径大小写、JSON/TOML、版本/modid 或网络注册；不要跳过门禁。
3. `build` 失败时，查看 `build-logs`；确认只产出一个符合排除规则的发布 Jar 及其 `mods.toml`。
4. 专服失败时，检查 Forge 安装、`logs/latest.log`、`crash-reports/` 和启动完成标志；客户端类引用或 Mixin 错误必须修复后重跑。
5. 客户端失败时，检查 Xvfb/Mesa 环境日志、`logs/latest.log` 和 crash-report；“进程曾启动”不是通过条件。
6. 修复后推送新提交或手动重跑工作流；只有 `regression-report` 显示所有必需 Job 成功，才可把本次构建作为候选产物。
